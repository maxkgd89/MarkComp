# Markdown Review Studio — Project Plan

**Version:** 1.2
**Status:** Milestones 1–6 implemented and tested
**Development environment:** VS Code with DSH-TUI
**Target platform:** Local Windows PC
**Primary file format:** Markdown (`.md`)

---

## 1. Project Purpose

Create a local application for working with Markdown documents generated by AI agents or written manually.

The application's primary purpose is to allow the user to compare an original Markdown document with a personally revised version while maintaining a clear understanding of the document's structure.

The application must make it easy to:

1. Navigate large Markdown documents without constant scrolling.
2. Read the original and revised documents side by side.
3. Identify exactly what has changed.
4. Edit the revised document without modifying the original.
5. Fold and unfold sections of the document.
6. Navigate between corresponding sections in both documents.
7. Scroll through both documents simultaneously.

The application is intended to be a document editing and comparison tool.

**AI assistance and agent communication are explicitly outside the application's scope.**

DSH-TUI will be used as the development environment, not as an integrated feature of the finished application.

---

## 2. Main Application Interface

The application must have three primary working areas.

### 2.1 Window 1 — Document Structure

Purpose: Display the hierarchical structure of the Markdown document.

Requirements:

- Automatically identify Markdown headings.
- Recognize heading levels H1 through H6.
- Display headings as a hierarchical tree.
- Support expanding and collapsing individual branches.
- Support expanding and collapsing entire document sections.
- Allow selecting a heading to navigate to its corresponding location in the documents.
- Maintain a clear visual distinction between different heading levels.

Example:

    Project Architecture
    |
    +-- 1. Introduction
    |   |
    |   +-- 1.1 Background
    |   +-- 1.2 Objectives
    |   +-- 1.3 Requirements
    |
    +-- 2. Backend
    |   |
    |   +-- 2.1 Database
    |   +-- 2.2 API
    |   +-- 2.3 Authentication
    |
    +-- 3. Frontend
        |
        +-- 3.1 Dashboard
        +-- 3.2 Settings

The structure tree must be generated automatically from the Markdown content.

The tree should reflect the actual heading hierarchy rather than relying exclusively on numerical prefixes.

### 2.2 Window 2 — Original Markdown

Purpose: Display the original version of the document.

Requirements:

- Load the original Markdown file.
- Display its contents in an editor-like view.
- Make the original document read-only.
- Preserve the original content without modifications.
- Support section folding and unfolding.
- Highlight differences relative to the revised document.
- Support synchronized scrolling with the revision window.

The original document must never be accidentally overwritten by editing operations.

### 2.3 Window 3 — My Revision Markdown

Purpose: Provide an editable working copy of the original document.

Requirements:

- Initially load a copy of the original Markdown.
- Allow unrestricted editing of the working copy.
- Support undo and redo of edits.
- Preserve Markdown formatting and syntax.
- Support section folding and unfolding.
- Highlight differences relative to the original document.
- Support synchronized scrolling with the original document.
- Allow saving the revised document independently.

The original document and revision document must remain separate.

## 3. Markdown Comparison

This is one of the application's central features.

Two comparison modes are required.

### 3.1 Side-by-Side Comparison

Display the original and revised Markdown documents next to each other.

Requirements:

- Original document on the left.
- Revised document on the right.
- Corresponding content should be visually aligned where possible.
- Added content must be highlighted.
- Removed content must be highlighted.
- Modified content must be identifiable.
- Highlighting must be visible in both document windows.

The comparison must distinguish between:

- Unchanged content.
- Added content.
- Removed content.
- Modified content.

### 3.2 GitHub-Style Diff Comparison

Provide a dedicated comparison mode similar to the diff interface used by GitHub.

Two presentation styles are required:

**Split Diff**

Display the original and revised content in separate columns.

**Unified Diff**

Display changes in a single column, showing additions and deletions together.

Visual conventions:

- Green highlighting for additions.
- Red highlighting for deletions.
- Clear indicators for modified lines.
- Word-level highlighting inside modified lines or paragraphs.

### 3.3 Word-Level Difference Highlighting

The comparison engine should identify changes within individual paragraphs, not only entire lines.

Example:

Original:

    The application supports basic Markdown editing.

Revision:

    The application supports advanced Markdown editing.

Expected result:

- "basic" identified as removed.
- "advanced" identified as added.
- Unchanged words remain visually unmarked.

This is important because highlighting an entire paragraph for a single word change would make large documents difficult to review.

Word-level difference detection will use Monaco Editor's built-in diff engine, with the `jsdiff` library as a fallback for custom decoration placement.

---

## 4. Synchronized Scrolling

The original and revised document windows must support synchronized vertical scrolling.

Requirements:

- Scrolling the original document automatically moves the revision document.
- Scrolling the revision document automatically moves the original document.
- Corresponding content should remain aligned as closely as possible.
- Synchronization must work when the documents contain different numbers of lines.
- Synchronization must account for inserted and deleted paragraphs.
- Synchronization must not create infinite scrolling feedback loops.

The comparison engine should use corresponding content positions rather than simply copying the same scroll offset.

A mechanism for temporarily disabling synchronization may be provided if necessary.

---

## 5. Markdown Structure Recognition

The application must automatically identify document structure.

### 5.1 Standard Markdown Headings

Recognize:

    # Heading 1
    ## Heading 2
    ### Heading 3
    #### Heading 4
    ##### Heading 5
    ###### Heading 6

These headings determine the hierarchy of the document tree.

When heading levels are skipped (for example, a document that jumps from `H1` directly to `H3`), the hierarchy must be resolved deterministically: a heading nests under the nearest preceding heading of a strictly lower level, so the tree always reflects a well-formed hierarchy rather than relying on numerical prefixes.

### 5.2 Nested Lists

Recognize nested numbered and unordered lists.

Example:

    - Main topic
        - Subtopic
            - Detail

Nested lists should preserve their original Markdown structure.

### 5.3 Other Markdown Elements

Recognize and preserve:

- Checklists.
- Blockquotes.
- Code blocks.
- Tables.
- Horizontal separators.
- Links.
- Images.

These elements must not be incorrectly interpreted as document headings.

### 5.4 GPT-Generated Markdown

Documents copied from ChatGPT or other AI conversations may contain inconsistent formatting.

The application should recognize standard Markdown structures even when the document contains:

- Multiple heading levels.
- Numbered sections.
- Nested bullet points.
- Separators between major sections.
- Mixed formatting.

If a line appears to be a heading but does not use standard Markdown heading syntax, it must not be silently converted.

The application may provide optional suggestions for recognizing such headings in a future iteration.

The original document must remain unchanged unless the user explicitly edits it.

---

## 6. Section Folding and Unfolding

Both Markdown document windows must support folding.

Requirements:

- Fold individual sections.
- Unfold individual sections.
- Fold all sections.
- Unfold all sections.
- Fold parent sections together with their nested subsections.
- Preserve the original Markdown content when folding.
- Preserve the revised Markdown content when folding.

Folding is a visual navigation feature.

It must not insert special folding markers into the Markdown files.

The document structure window should also allow independent collapsing of tree branches.

Folding a tree branch and folding document content should be treated as separate operations.

---

## 7. Navigation Between Documents

The structure tree must provide navigation across both document windows.

Requirements:

1. Selecting a heading in the structure tree navigates to the corresponding heading in the original document.
2. The same selection navigates to the corresponding heading in the revision document.
3. Navigation must work even when the documents have different line counts.
4. If a heading has been renamed in the revision, the application should attempt to identify its corresponding original section.
5. If a corresponding section cannot be identified reliably, the application must not navigate to an unrelated section.

The navigation mechanism should rely on document structure and heading relationships, not exclusively on line numbers.

---

## 8. Document Management

Minimum functionality:

- Open an existing Markdown file.
- Load it as the original document.
- Create an editable revision copy.
- Save the revision independently.
- Save the revision under a different filename.
- Reload the original document when starting a new comparison.
- Preserve the original file.

The application must clearly distinguish between the original and revised documents.

A user must never accidentally save the revision over the original.

## 9. Development Milestones

Development should proceed incrementally.

Each milestone must be tested and approved before moving to the next.

### Milestone 1 — Interface Prototype

Objective: Establish the three-window interface.

Deliverables:

- Structure panel.
- Original Markdown panel.
- Revision Markdown panel.
- Resizable panels.
- Basic document loading.
- Basic editing in the revision panel.

Acceptance criteria:

- All three areas are visible.
- The structure panel can display headings.
- The original document is read-only.
- The revision document is editable.
- Panel sizes can be adjusted.
- The application can open a sample Markdown document.

### Milestone 2 — Markdown Structure and Folding

Objective: Implement document hierarchy and navigation.

Deliverables:

- Heading recognition H1–H6.
- Hierarchical document tree.
- Expand/collapse tree branches.
- Section folding in both documents.
- Fold all / unfold all.
- Navigation from the tree to document headings.

Acceptance criteria:

- Nested headings appear at the correct hierarchy level.
- Collapsing a parent hides its children in the tree.
- Folding a section hides its content without modifying the Markdown.
- Navigation selects the corresponding section in both documents.

### Milestone 3 — Side-by-Side Comparison

Objective: Implement comparison between original and revised documents.

Deliverables:

- Original/revision comparison.
- Content alignment.
- Added content highlighting.
- Removed content highlighting.
- Modified content highlighting.
- Word-level difference detection.

Acceptance criteria:

- Unchanged content is not highlighted.
- Added content is identifiable.
- Removed content is identifiable.
- Individual word changes are highlighted.
- Differences remain understandable after inserting or deleting paragraphs.

### Milestone 4 — GitHub-Style Diff

Objective: Implement dedicated diff presentation.

Deliverables:

- Split diff mode.
- Unified diff mode.
- Green additions.
- Red deletions.
- Modified line identification.
- Word-level highlighting.
- Navigation between changes.

Acceptance criteria:

- Both diff modes display the same underlying changes.
- Additions and deletions are correctly represented.
- Modified words are identifiable.
- The user can navigate between changes.

### Milestone 5 — Synchronized Scrolling

Objective: Synchronize original and revision document navigation.

Deliverables:

- Bidirectional scrolling synchronization.
- Corresponding content alignment.
- Synchronization across inserted and deleted content.
- Optional synchronization toggle.

Acceptance criteria:

- Scrolling either document moves the other.
- Corresponding sections remain aligned.
- Different document lengths do not break synchronization.
- No infinite synchronization loops occur.
- Folding and unfolding do not permanently break synchronization.

### Milestone 6 — Integration and Final Testing

Objective: Verify the complete application.

Deliverables:

- File opening and saving.
- Full interface integration.
- Document structure integration.
- Comparison integration.
- Scrolling integration.
- Final usability testing.

Acceptance criteria:

- All previously approved functionality works together.
- Original documents remain unchanged.
- Revised documents can be saved independently.
- Large Markdown documents remain usable.
- No major navigation or comparison errors remain.

## 10. Test Document Requirements

Development must use realistic Markdown documents rather than only small artificial examples.

The primary test document should contain:

- 10 main topics.
- Between 3 and 10 subsections per topic.
- At least three heading levels.
- Nested numbered lists.
- Nested bullet lists.
- Checklists.
- Tables.
- Code blocks.
- Blockquotes.
- Horizontal separators.
- Long paragraphs.
- Links.

Additional tests should include:

1. A document copied directly from a ChatGPT conversation.
2. A document with inconsistent heading formatting.
3. A document with missing heading levels.
4. A document with large inserted sections.
5. A document with deleted sections.
6. A document with reordered sections.
7. A document with small word-level changes.
8. A document with substantial differences between original and revision.

## 11. Explicitly Excluded Features

The following functionality is not part of this project:

- AI assistant inside the application.
- Direct integration with DSH-TUI sessions.
- Sending instructions to AI agents.
- Automatic AI document correction.
- AI-generated comments.
- Comments attached to paragraphs.
- Accept/reject individual changes.
- Approval workflows.
- Review statuses.
- Collaborative editing.
- Cloud synchronization.
- Additional project management functionality.

The application is strictly a local Markdown editing, navigation and comparison tool.

---

## 12. Important Development Principles

1. Preserve original Markdown files.
2. Never silently modify document content during import.
3. Treat Markdown headings as structural elements.
4. Keep folding independent of the actual Markdown content.
5. Make document comparison understandable even when substantial changes occur.
6. Prioritize accurate comparison over visual effects.
7. Keep the interface focused on the three primary working areas.
8. Avoid adding functionality that does not directly support the agreed workflow.
9. Test each milestone before proceeding.
10. Do not begin full implementation until the interface prototype has been reviewed and approved.

---

## 13. Definition of Success

The project is successful when the user can:

1. Open an original Markdown document.
2. Automatically see its hierarchical structure.
3. Navigate large documents using the structure tree.
4. Fold and unfold sections in both document windows.
5. Edit an independent revision of the original document.
6. Compare original and revised versions side by side.
7. Identify added, removed and modified content.
8. Use GitHub-style split and unified diff modes.
9. Identify word-level changes.
10. Scroll through both documents simultaneously while keeping corresponding content aligned.
11. Save the revised Markdown without modifying the original.

**The finished application should make reviewing and revising large AI-generated Markdown documents significantly easier than working with two separate text files.**

## 14. Technical Stack

The application is implemented with the following stack:

- **Runtime:** Electron (local Windows desktop app).
- **Language:** TypeScript.
- **UI:** React for the panel layout, structure tree, and diff/scroll state.
- **Editors:** Monaco Editor (`monaco-editor` directly, behind a small React wrapper) for all three panes — it provides Markdown syntax highlighting, heading-based folding (custom provider), and a diff editor (split + inline/unified) with word-level diff out of the box.
- **Build tooling:** electron-vite for development and bundling; electron-builder for packaging (final, optional step).
- **Diff engine:** Monaco Editor's built-in diff engine for the dedicated diff view, with the `diff` package (jsdiff) for line/word computation and custom decoration placement in the editable panes.

Two diff surfaces are used deliberately:

- The **editable revision pane** (Window 3) is a normal Monaco editor with inline diff **decorations** so it stays fully editable while showing differences.
- The **dedicated GitHub-style diff mode** (Milestone 4) uses Monaco's read-only `createDiffEditor` for split and unified views.

The structure tree uses a lightweight, custom regex-based heading parser (H1–H6); no heavy Markdown library is required.
